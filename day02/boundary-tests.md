# Day 02：責任邊界測試

## 測試輸入

> 登入功能怪怪的，有時候會失敗。

來源：Day 01 `raw-issues.md` 第 1 筆。本測試以人工智慧（Artificial Intelligence，以下簡稱 AI）協作為範圍。

## 測試方法

對每個候選輸出依序檢查：

1. 是否可追溯到輸入或既有規格？
2. 錯誤通過後是否容易發現與復原？
3. 是否需要正式權限或組織情境？
4. 應歸入 L0、L1、L2 或 L3？
5. 最終責任角色是誰？

## 反例檢查

### 反例一：用語流暢但新增事實

超文字傳輸協定（Hypertext Transfer Protocol，以下簡稱 HTTP）的 500 狀態碼代表伺服器錯誤類型；下列內容卻沒有任何來源支持這項判斷：

```text
正式環境的 Google 登入偶發 HTTP 500，建議由帳號服務團隊緊急修復。
```

問題：

- 「正式環境」「Google 登入」「HTTP 500」沒有來源。
- 「帳號服務團隊」沒有服務目錄依據。
- 「緊急」沒有影響與服務等級依據。

結論：不通過。應退回已知事實與未知欄位。

### 反例二：有人工按鈕但沒有有效覆核

```text
審查者只能看到 AI 摘要，看不到原始回報；介面只有「同意」按鈕。
```

問題：

- 無法核對來源。
- 無法修改、退回或記錄理由。
- 不知道審查者是否具備決定權。

結論：不構成有效人工覆核。

## 測試結論

- L1 草稿必須能逐項回到來源。
- L2 候選不得在介面或資料結構中偽裝成已確認值。
- L3 欄位必須指定實際責任角色及決策依據。
- 顯示人工核准按鈕，不等於已建立有效監督。
