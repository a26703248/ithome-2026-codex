# Day 26 治理盤點紀錄

本文件是依 `案例/AI輔助生成系統-需求書.md` 製作的桌上演練，記錄開發團隊自己使用 Codex 時的
使用案例盤點與治理骨架，不是已核定的公司政策，也不是真實跨部門會議紀錄。

## 觸發事件

工程師使用 Codex 為「AI 輔助生成系統」的 OCR／ETL 前處理補單元測試，測試資料使用真實客戶
上傳的掃描檔案。需求書第五節要求資料依敏感度分級、含個資時可去識別化，但公司內部尚未訂出
具體分級標準，工程師因此沒有依據可以判斷這批測試資料是否可用。

## 使用案例盤點

| 盤點項目 | 本案例內容 | 主要風險 | 建議負責角色 |
|---|---|---|---|
| 使用目的 | 用 Codex 補 OCR／ETL 前處理測試、調整 AI 草稿生成邏輯 | 把測試任務範圍當成可以碰生產資料的理由 | 工程主管核准任務範圍 |
| 輸入資料 | 測試資料是否使用真實客戶上傳文件、是否含個資 | 個資或機密文件外流到外部服務或版本控制紀錄 | 法遵／資安核定分級與去識別化規則 |
| 工具與權限 | Codex 可讀寫的程式碼與測試資料目錄、能否連外部網路 | 權限過寬，誤讀客戶資料庫或機密設定 | 系統管理者限制存取範圍 |
| 輸出用途 | 修改是否直接進入正式分支、是否先經 Code Review | 未經審查的變更混入正式環境 | 覆核人員／工程主管把關合併 |
| 外部依賴 | Codex 所屬雲端執行環境、OCR／ETL 套件來源 | 資料傳輸到供應商牽涉的合規責任 | 法遵／資安評估供應商條款 |

## 治理骨架（六個面向）

| 治理面向 | 現況 | 缺口 | 下一步控制 |
|---|---|---|---|
| 權限與資料分級 | 需求書要求依角色分級管控存取，公司內部分級標準未訂 | 沒有「哪個角色能碰哪一級資料」的清單 | 先訂公開／內部／限閱三級示範分類 |
| 稽核與操作紀錄 | 系統設計要求保留每步操作與版本歷程 | 開發團隊自己用 Codex 的操作沒有對應紀錄 | 任務範圍、核准人、Codex 執行紀錄一併留存 |
| 人工覆核 | 系統預設覆核後才能匯出或標記完成 | Code Review 未對觸及分級邏輯的變更加嚴 | 觸及存取控制或分級邏輯的異動要求雙人覆核 |
| 事件與通報 | 目前多半靠口頭反映 | 沒有標準通報表單與處理時限 | 訂通報窗口、24 小時內回報、留存影響範圍 |
| 供應商與變更 | 沒有紀錄 Codex、OCR 套件的版本異動 | 條款或模型更新後沒有重新評估流程 | 版本或條款變動時觸發重新風險評估 |
| 效果與改善 | 沒有定期檢討治理措施是否落地 | 文件寫了，沒人追蹤執行率 | 每季檢討一次，把否決與事故案例回饋進 SOP |

## 待角色確認

| 待確認事項 | 建議責任角色 | 可接受的驗收證據 |
|---|---|---|
| 公開／內部／限閱三級的實際判定標準 | 法遵／資安 | 核定分級表與範例 |
| ETL／OCR 測試資料是否一律要求去識別化或合成資料 | 法遵、工程主管 | 測試資料來源規範與抽查紀錄 |
| Codex 可連線的網路範圍與套件白名單 | 系統管理者、資安 | 設定檔、白名單清單 |
| 事故通報表單與 24 小時時限是否可行 | 工程主管、法遵 | 通報流程文件與一次演練紀錄 |
| ISO/IEC 42001 或同等標準的具體對照方式 | 法遵、資安 | 對照表、內部稽核紀錄 |
