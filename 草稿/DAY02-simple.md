# Day 02｜ChatGPT vs Codex：對話助手與沙箱編程代理的差異

> 文件用途：這是作者擴寫用的文章結構，不是可直接發布的完稿。全文完成後建議控制在 900～1,100 字，並以實際任務證明工具分工。

## 開場：同一個問題，不一定交給同一個工具

**撰寫範圍（100 字內）：** 從一項 Java 開發任務切入，描述只需要討論方案與需要直接進入專案修改，為何是兩種不同需求。

### 作者撰寫區塊

> 假設今天產品端回報一個問題是"站台的查詢結果好像怪怪的"，這時候我們有兩個選項;第一直接將問題原封不動的拿給ChatGPT詢問，第二將問題和產品相關規格書丟給Codex，請他幫忙讀取後再針對問題進行修改，兩種做法沒有誰對誰錯都能夠完成只要問題能夠清楚且提供明確的資訊基本上問題都能解決，但這兩者卻在對話的交互次數上卻有非常明顯的差異，這將會大大影響整體工作的效率，所以我們必須要在收到問題的時後明確知道現在該用哪個工具來協助我們完成

## 先建立兩種工作心智模型

**撰寫範圍（100 字內）：** 說明 ChatGPT 以對話、內容理解與產出為核心；Codex 則在授權環境內讀取檔案、修改專案、執行工具並回報結果。

### 作者撰寫區塊

> 首先"站台的查詢結果好像怪怪的"是事實，但對於後續問題的追蹤卻毫無任何幫助，這時候我們可以透過ChatGPT引導我們自己需要確認那些資訊，目前狀況可能會有的方向，最後在生成一份完整的 Issue Report。之後再將這一份完整 Issue Report、產品規格書、產品流程圖和產品程式碼交給codex做修改。
> **作者的話:ChatGPT生成的完整報告皆有可能是模型自行幻想或是網路上文章，內容不一定符合讀者當下問題與情境，故需要針對生成內容進行人工確認**

**撰寫範圍（100 字內）：** 比較互動方式、上下文來源、可執行動作、主要產出與驗證方法，建立比功能清單更耐用的判斷架構。

### 作者撰寫區塊

> 請完成下表，內容以發布當日實測及官方文件為準。

| 比較維度 | ChatGPT             | Codex       | 作者觀察                                             |
|---|---------------------|-------------|--------------------------------------------------|
| 主要互動方式 | 多輪對話方式              | 閱讀檔案文件      | 當問題較為開放或是沒有一個目標可考慮用ChatGPT;當問題是已知且範圍有邊界時可考慮Codex |
| 上下文來源 | 網址、上傳檔案、雲端硬碟或App    | 指定專案內所有檔案   | ChatGPT和codex相比多出了網路資訊                           |
| 可執行動作 | 執行計畫、網站生成、深入研究、圖檔生成 | 檔案閱讀修改、圖檔生成 | 基本上此項兩者差不多                                       |

| 驗證方式 | 待填                  | 待填          | 兩者扮演角色不同故不做比較                                               |
| 常見風險 | 待填                  | 待填          | 資安考量、權限問題                                        |

**作者的話:隨者時間的推移ChatGPT的功能也慢慢的在Codex上能夠使用，所以兩者差異後續只會越來越小**

## 任務一：釐清模糊需求，先用 ChatGPT

**撰寫範圍（100 字內）：** 示範如何請 ChatGPT 追問角色、輸入、例外、限制與驗收條件，重點是補齊思考，不是立即產生程式碼。

### 作者撰寫區塊

> 原始需求：站台的查詢結果好像怪怪的。
>
> 我提供的背景與限制：目前狀況重新操作一次無法重現。
>
> ChatGPT 提出的有效問題：
> 問題由哪一類使用者發現？當時使用的環境、裝置、帳號權限、輸入關鍵字、篩選條件、排序方式與操作步驟為何？預期結果和實際結果有何差異？是否涉及空值、特殊字元、大量資料、跨頁、逾時或資料更新等例外情境？有哪些功能或商業規則不能變更？PM、工程師與 QA 應如何共同判定問題已修正？
>
> 我刪除或修正的錯誤假設：
> 刪除「一定是後端查詢程式錯誤」、「無法重現就代表問題不存在」及「查詢結果怪異的判斷標準大家都一致」等未經證實的假設。改為分別確認前端顯示、輸入條件、資料內容、快取、權限、環境及資料同步差異。

### 作者驗證案例

- [ ] ChatGPT 有指出資訊不足處，而不是自行補完商業規則。
- [ ] 最終產出包含可由 PM、工程師與 QA 共同確認的驗收條件。
- [ ] 作者逐項核對需求，沒有把模型推測當成既定事實。

## 任務二：修正可重現的缺陷，再交給 Codex

## 選擇工具的判斷表

**撰寫範圍（100 字內）：** 將常見任務放進簡單決策表，說明需要發散思考、討論與整理時，以及需要操作專案、執行驗證時的選擇。

### 作者撰寫區塊

| 任務 | 建議先用    | 判斷理由                       | 交付前仍需人工確認             |
|---|---------|----------------------------|-----------------------|
| 把 user story 補成驗收條件 | ChatGPT | 驗收條件可能不會侷限於 user story 描述中 | user story 描述情境是否皆有包含 |
| 比較兩個架構方案 | ChatGPT | 兩個架構的資訊需要透過查詢網路資訊才能更清楚的比較  | 提供資訊是否有誤或偏離事實         |
| 修正可重現的 Java 缺陷 | Codex   | 已經明確知道問題範圍                 | 單元測試是否通過              |
| 補上 JUnit 5 測試 | Codex   | 已明確知道驗收條件和業務邏輯範圍           | Test Case 是否皆有包含      |
| 說明陌生程式碼 | Codex   | 已有存在程式碼可供參考                | 程式碼是否可證明出處            |
| 修改跨模組相依關係 | Codex   | 已明確調整範圍                    | 測試是否通過                |

**作者的話:我的定義比較像是ChatGPT用來增加或是驗證知識盲區，Codex實作已知範圍內或心中已有答案的事情**

## 邊界：兩者都不能取代驗證與責任
