# Day 23｜安全與程式碼品質把關

> 系列階段：第 3 週｜進階整合工作流
>
> 共用案例：`案例/日報服務-需求書.md`（Day 17–23 共用，本篇聚焦處理那筆未確認的套件安全性通知）。
>
> 文件用途：作者擴寫用文章骨架，建議完稿控制在 900～1,100 字，以 Java 修改建立可操作的安全與品質檢查流程。

## 開場情境：功能測試通過，仍可能帶著風險上線

**撰寫範圍（100 字內）：** 從輸入驗證不足、祕密外洩、相依風險或錯誤處理缺陷開場，說明正確性只是程式品質的一部分。

### 作者撰寫區塊

#### AI 建議

> 需求書現況那一節留了一條沒人處理的線索：PDF 產生套件的更新紀錄裡，有一筆尚未確認是否影響本系統的安全性通知。Day 17 到 Day 22 陸續拆開排程、產製、寄信邏輯，也新增了格式與頻率，這些修改都通過了功能測試，但沒有人回頭確認過那筆通知，也沒人重新檢查新增的 WORD、EXCEL 產生流程有沒有帶進新的相依風險。品質把關不能只問「功能能不能用」，還要看失敗時會暴露什麼、影響多大。

> 請選一項 AI 建議中容易被忽略的安全或品質問題，寫下為何單元測試可能看不出來，以及可能造成的影響。

## 核心概念：建立分層檢查清單

**撰寫範圍（100 字內）：** 從需求、程式碼、相依套件、資料、執行環境與維運六層檢查 AI 生成修改，避免只靠單一掃描工具。

### 作者撰寫區塊

#### AI 建議

> 檢查清單可分成需求正確性、輸入與權限、資料與祕密、錯誤處理、相依與供應鏈、並行與效能、測試與可維護性。針對日報服務，相依與供應鏈這一項要特別把那筆套件安全性通知，以及新增 WORD、EXCEL 產生套件的來源與版本一起納入，每項都要求證據，例如測試、設定、靜態分析或人工威脅情境，而不是只勾選「已檢查」。

| 檢查層次 | 主要問題 | 使用的證據或工具 |
|---|---|---|
| 需求與權限 | 待填 | 待填 |
| 程式碼行為 | 待填 | 待填 |
| 相依套件 | 那筆尚未確認的 PDF 套件安全性通知，以及新增的 WORD、EXCEL 產生套件 | 待填 |
| 資料與祕密 | 待填 | 待填 |
| 執行環境 | 待填 | 待填 |

## 實作示範：審查一段 AI 生成的 Java 修改

**撰寫範圍（100 字內）：** 使用可公開的 Spring Boot 端點，依輸入驗證、授權、例外、日誌、相依與測試逐項檢查並修正。

### 作者驗證案例

- [ ] 外部輸入有明確驗證、長度與格式限制。
- [ ] 身分驗證與授權沒有被混為一談。
- [ ] 錯誤訊息與 log 不洩漏敏感資訊。
- [ ] 新增相依套件有必要性、來源與版本風險檢查。
- [ ] 測試包含未授權、惡意輸入與失敗路徑。
- [ ] 靜態分析或安全掃描結果已人工判讀。

## 實作示範：把檢查清單交給 Codex 初篩

**撰寫範圍（100 字內）：** 要求 Codex 逐項提出證據、未知與建議測試，再由作者用工具與程式脈絡確認，不直接採納結論。

### 作者撰寫區塊

#### AI 建議

> 交給 Codex 初篩時，要求它指出檔案位置、觸發條件、可能影響與驗證方式，並允許回覆「證據不足」。針對那筆安全性通知，也可以先讓 Codex 查目前套件版本、比對通知內容是否命中本系統實際使用的功能，列出「是否要納入本次範圍」的判斷依據，最後仍由人決定，不是工具說沒事就沒事。

> 請保留一項有效發現、一項誤報及一項 Codex 漏掉的問題，說明人工與自動化工具如何補足。

## 效益與注意事項

**撰寫範圍（100 字內）：** 說明一致清單可降低遺漏，但安全檢查需要威脅脈絡與持續更新，AI 與掃描工具都可能誤報或漏報。
