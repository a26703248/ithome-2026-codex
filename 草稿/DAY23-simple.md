# Day 23｜安全與程式碼品質把關

> 系列階段：第 3 週｜進階整合工作流
>
> 文件用途：作者擴寫用文章骨架，建議完稿控制在 900～1,100 字，以 Java 修改建立可操作的安全與品質檢查流程。

## 開場情境：功能測試通過，仍可能帶著風險上線

**撰寫範圍（100 字內）：** 從輸入驗證不足、祕密外洩、相依風險或錯誤處理缺陷開場，說明正確性只是程式品質的一部分。

### 作者撰寫區塊

#### AI 建議

> 一段 Java 修改可以通過功能測試，仍可能把權限檢查放錯層、把敏感值寫進執行紀錄（log），或用沒有限制的外部輸入組合查詢。品質把關不能只問「功能能不能用」，還要看失敗時會暴露什麼、影響多大。

> 請選一項 AI 建議中容易被忽略的安全或品質問題，寫下為何單元測試可能看不出來，以及可能造成的影響。

## 核心概念：建立分層檢查清單

**撰寫範圍（100 字內）：** 從需求、程式碼、相依套件、資料、執行環境與維運六層檢查 AI 生成修改，避免只靠單一掃描工具。

### 作者撰寫區塊

#### AI 建議

> 檢查清單可分成需求正確性、輸入與權限、資料與祕密、錯誤處理、相依與供應鏈、並行與效能、測試與可維護性。每項都要求證據，例如測試、設定、靜態分析或人工威脅情境，而不是只勾選「已檢查」。

## 實作示範：審查一段 AI 生成的 Java 修改

**撰寫範圍（100 字內）：** 使用可公開的 Spring Boot 端點，依輸入驗證、授權、例外、日誌、相依與測試逐項檢查並修正。

### 作者驗證案例

- [ ] 外部輸入有明確驗證、長度與格式限制。
- [ ] 身分驗證與授權沒有被混為一談。
- [ ] 錯誤訊息與 log 不洩漏敏感資訊。
- [ ] 新增相依套件有必要性、來源與版本風險檢查。
- [ ] 測試包含未授權、惡意輸入與失敗路徑。
- [ ] 靜態分析或安全掃描結果已人工判讀。

## 實作示範：把檢查清單交給 Codex 初篩

**撰寫範圍（100 字內）：** 要求 Codex 逐項提出證據、未知與建議測試，再由作者用工具與程式脈絡確認，不直接採納結論。

### 作者撰寫區塊

#### AI 建議

> 交給 Codex 初篩時，要求它指出檔案位置、觸發條件、可能影響與驗證方式，並允許回覆「證據不足」。高風險結論仍須由人重現與判定；工具沒有找到問題，也不能當作安全保證。

> 請保留一項有效發現、一項誤報及一項 Codex 漏掉的問題，說明人工與自動化工具如何補足。

## 效益與注意事項

**撰寫範圍（100 字內）：** 說明一致清單可降低遺漏，但安全檢查需要威脅脈絡與持續更新，AI 與掃描工具都可能誤報或漏報。
