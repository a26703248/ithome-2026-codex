# Day 22｜文件與註解自動化

> 系列階段：第 3 週｜進階整合工作流
>
> 共用案例：`案例/日報服務-需求書.md`（Day 17–23 共用，本篇聚焦修正過時的專案說明檔）。
>
> 文件用途：作者擴寫用文章骨架，建議完稿控制在 900～1,100 字，以程式碼與測試為來源補齊可驗證文件。

## 開場情境：最危險的文件是看起來完整但已過時

**撰寫範圍（100 字內）：** 從 README 指令失效、註解與實作不符或維運步驟缺漏的案例開場，說明生成速度不能解決資料來源錯誤。

### 作者撰寫區塊

#### AI 建議

> 日報服務的專案說明檔（README）記錄的仍是舊版啟動參數與設定檔位置，目前的排程觸發方式、環境變數與部署方式都已經和文件描述不同——這是需求書自己列出的現況，不是猜測。一份寫著舊版啟動參數的 README，比沒有文件更容易讓新同事走錯。請 Codex 補文件前，應先依專案定義可信來源的優先順序，例如目前的排程設定、Day 18 拆出來的程式結構、測試與持續整合（Continuous Integration，CI）；來源衝突時交由人判定。

> 請選一份真實但可公開的過時文件，指出讀者會在哪一步失敗，以及程式碼、測試或設定中的正確證據。

## 核心概念：先找可信來源，再決定生成內容

**撰寫範圍（100 字內）：** 依程式碼、測試、設定、執行輸出與人工決策排序資料來源，避免 Codex 用命名猜測未被證明的系統行為。

### 作者撰寫區塊

#### AI 建議

> 每一句文件都應能連回來源。例如排程觸發方式來自目前的設定類別與實際執行結果，報表產製與寄信的行為來自 Day 18、Day 20 已經確認過的程式路徑與特徵測試；無法確認或彼此衝突的內容標成待查，不讓 Codex 用合理文字填滿空白，例如週、雙週、月報表的數值計算範圍需求書本身還沒定義，就不能寫成文件裡的既定行為。

## 實作示範：讓 Codex 補齊 README 一節

**撰寫範圍（100 字內）：** 指定讀者、範圍與證據來源，讓 Codex 草擬安裝、執行或測試段落，再逐條執行文件中的步驟。

### 作者驗證案例

- [ ] 文件中的每個指令均在指定環境實際執行。
- [ ] 版本、路徑、環境變數與預設值符合專案。
- [ ] 缺少證據的內容已標成待確認而非自行補寫。
- [ ] 指令範例不含金鑰、內部網址或個人資料。
- [ ] 新手依文件能完成目標，沒有隱藏前置步驟。

## 實作示範：只在必要處補註解

**撰寫範圍（100 字內）：** 比較重述程式碼與說明設計理由的註解，保留後者並刪除容易隨實作變動的冗餘說明。

### 作者撰寫區塊

#### AI 建議

> 註解應說明程式碼本身看不出的「為什麼」，例如某段成長率計算為什麼要對比「上一個相同頻率的週期」而不是單純的前一天，是為了配合新的日、週、雙週、月報表需求；不要逐行翻譯迴圈在做什麼。補完後再請熟悉領域的人核對，避免把歷史推測寫成正式規則。

> 請挑一段非直覺 Java 邏輯，分別展示「描述做什麼」與「說明為什麼」的註解，再解釋最後保留哪一版。

## 效益與注意事項

**撰寫範圍（100 字內）：** 說明 Codex 可加速盤點與初稿，但文件若沒有驗證與維護責任，生成越多反而累積越快的技術債。
