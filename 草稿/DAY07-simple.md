## 開場情境：API 能呼叫，不代表契約清楚

**撰寫範圍（100 字內）：** 從前後端對欄位、錯誤碼或邊界條件理解不同的案例開場，帶出 API 契約需要先於範例程式碼被確認。

### 作者撰寫區塊

#### AI 建議

> 示例情境：前端已能呼叫工作區空間的資料匯入端點，整合時才發現後端把「欄位格式不符」回成 500，前端卻預期 422。這不是 OpenAPI 自行決定；若原因是請求內容本身不符合驗證規則，422 較能表達語意，500 則表示伺服器遇到未預期狀況，團隊仍須在契約中明確定義，需求書第七節提到的「資料格式是否一致」在這裡直接變成一個要選定狀態碼的具體問題。

> 請描述一次 API 溝通落差：哪個欄位或行為被誤解？造成什麼返工？若涉及真實系統，請去除內部網址與商業資料。

## 核心概念：先確定契約，再請 ChatGPT 整理格式

**撰寫範圍（100 字內）：** 說明需求、資料型別、驗證規則、狀態碼與錯誤格式須由團隊確認，ChatGPT 適合協助轉成一致的規格草稿。

### 作者撰寫區塊

#### AI 建議

> 我會先確認匯入資源長什麼樣子、哪些欄位必填、排程觸發與客戶手動觸發是否共用同一個端點，再請 ChatGPT 整理成 OpenAPI 結構。模型可以檢查欄位是否遺漏，卻不能自行決定「一個工作區可以同時處理幾個匯入批次」這類需求書本身也還沒定義的規則。

## 實作示範：從需求到 OpenAPI 草稿

**撰寫範圍（100 字內）：** 以一個 Spring Boot 端點示範輸入需求、產生 OpenAPI schema、補範例及核對 controller 行為的完整流程。

### 作者撰寫區塊

#### AI 建議

> 示例可從 `POST /workspaces/{workspaceId}/imports` 開始，明確寫出路徑參數、成功回應、未授權、欄位格式不符與工作區不存在等案例。這個端點是作者依 Day 04、Day 05 的釐清結果自行設計的示範，需求書本身沒有規定端點命名，須在文章中誠實標明。產生草稿後，再用 OpenAPI 驗證工具檢查語法，並由實作者核對狀態碼與資料綱要（schema）是否符合現有慣例。

> 請挑選一個範圍小的端點，附上必要的 Java 類別或去識別化介面。提示詞須要求標記未知資訊，不得自行編造欄位與狀態碼。

### 作者驗證案例

## 延伸實作：由規格產生呼叫範例

**撰寫範圍（100 字內）：** 在契約已核對後，產生請求與回應範例，並說明範例只能協助理解，不能取代自動化契約測試。

### 作者撰寫區塊

#### AI 建議

> 呼叫範例至少準備成功與一個失敗案例（例如兩種來源欄位對不齊時的錯誤回應），讓讀者看見錯誤回應不是附錄。Java 範例應只示範如何依契約送出請求與處理狀態，不要把權杖、內部網址或未驗證的軟體開發套件（Software Development Kit，SDK）用法寫進文章。

> 請選擇 curl 與 Java client 範例各一，實際執行後記錄結果。若環境無法執行，須清楚標示為未驗證草稿。
