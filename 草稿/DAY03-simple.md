## 開場：一個小修正，為什麼要在視窗之間來回搬運？

**撰寫範圍（100 字內）：** 從處理 Java 小修正時，反覆在對話視窗、IDE 與終端機之間複製需求、程式碼及測試結果的情境切入，帶出環境入口會影響上下文是否完整，以及工作流程能否形成短回饋迴圈。

### 作者撰寫區塊

#### AI 建議

> 我曾經處理一項範圍不大的 Java 修正：先在 ChatGPT 說明需求，再把程式碼貼進對話，接著回到 IDE 修改，最後切到終端機執行測試。測試失敗後，又得把錯誤訊息貼回原本的對話。真正耗時的不是修改本身，而是每切換一次入口，就要重新補齊上下文。這段經驗讓我開始思考：ChatGPT App、Web、API，以及 Codex CLI、IDE 擴充功能與 cloud，分別應該放在工作流程的哪個位置？此處請換成作者親自遇過的任務、切換過程與實際感受。

> 上一章節已經提到了 ChatGPT和 Codex之間存在的差異和選對工具是一件非常重要的事情。今天這一章節主要是來介紹目前 ChatGPT 有融入了哪一些工具，讓我在工作上時不需要一直不停反覆的切換視窗，這將會大大的影響我們的專注力和心流

## ChatGPT 的三種入口：App、Web 與 API

**撰寫範圍（100 字內）：** 比較桌面應用程式、網頁與應用程式介面適合的互動方式，聚焦日常討論、檔案處理及系統整合，不逐項背功能。

### 作者撰寫區塊

#### AI 建議

> 可把 App 與 Web 寫成「持續對話、整理需求與檢視檔案」的互動入口，把應用程式介面（Application Programming Interface，API）寫成「由程式觸發、需要明確輸入輸出與成本控管」的整合入口。例如，單次討論例外流程可用 ChatGPT；需要自建批次整合時，才評估 OpenAI API。實際能力與方案限制須在發布日查證。

| 入口 | 適合情境             | 不適合情境       |
|---|------------------|-------------|
| ChatGPT App | 日常需要透過語音、照相等功能提問 | 需要大量閱讀/編輯長文、多工比對多個分頁資料、深度研究型任務  |
| ChatGPT Web | 臨時對話             | 需要深度融入日常工作的 |
| OpenAI API | 商業用開發            | 公開專案        |

> ChatGPT App與ChatGPT Web功能上基本沒有差異，除了一些語音、相機等相關功能Web沒有外其餘功能差不多，所以可以依照個人使用習慣做挑選就好。OpenAI API則屬於較為彈性的商業開發，對於個人工作流程而言有點過於複雜在此就不多做描述

## Codex 的三種入口：CLI、IDE 擴充功能與 Codex cloud

**撰寫範圍（100 字內）：** 比較終端機、編輯器整合與雲端任務的操作距離、上下文、執行環境及審查方式，避免將三者視為同一介面。

### 作者撰寫區塊

#### AI 建議

> Codex 命令列介面（Command-Line Interface，CLI）可示範在終端機中讀取本機專案並跑 Maven 測試；Codex 整合開發環境（Integrated Development Environment，IDE）擴充功能可示範局部修正；Codex cloud 則適合範圍明確、能在遠端環境重建的任務。三者都應以程式差異（diff）、測試結果與人工審查驗收。

| 入口          | 適合情境                        | 不適合情境      |
|-------------|-----------------------------|------------|
| Codex CLI   | 需要直接用終端機操作情況                | 需要人工修改生成結果 |
| Codex App   | 日常開發工作                      | 資料查詢       |
| Codex cloud | 想將Github Issue、PR 交給Agent處理 | 程式碼調整與修改   |

> Codex App與Codex CLI屬於相同的工具，所以可以依照環境上的限制來去挑選。Codex cloud 方面則比較多為 gitflow 的流程處理。
