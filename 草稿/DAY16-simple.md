## 開場情境：程式改完了，團隊仍需要可審查紀錄

**撰寫範圍（100 字內）：** 從工作目錄混入多項修改或 commit 說明不清的情境開場，帶出 Git 能保存範圍、意圖與審查節點。

### 作者撰寫區塊

> 請描述一次變更難以審查或回復的經驗：問題出在分支、commit 範圍、訊息，還是未分離使用者既有修改？

## 核心概念：Git 是證據鏈，不是完成按鈕

**撰寫範圍（100 字內）：** 說明分支隔離工作、diff 呈現改動、commit 保存意圖、Pull Request 承載審查，但都不能取代測試與人工判斷。

| 工作目錄 | 待填 | 待填 |
| Commit | 待填 | 待填 |

## 實作示範：從乾淨分支到 PR 草稿

**撰寫範圍（100 字內）：** 以 Day 13 的修正為例，記錄檢查狀態、建立分支、修改測試、審查 diff、提交及產生 PR 草稿的順序。

### 作者驗證案例

- [ ] 開始前已辨識並保留使用者既有修改。
- [ ] 分支名稱能對應任務，且不直接在受保護分支工作。
- [ ] Commit 只包含本任務檔案，訊息說明原因與結果。
- [ ] PR 草稿列出測試證據、風險與未完成事項。
- [ ] 沒有在未獲授權時自行推送、建立 PR 或合併。

### 作者撰寫區塊


## 實作示範：發現工作目錄不乾淨時怎麼辦

**撰寫範圍（100 字內）：** 用安全案例說明遇到既有修改時，Codex 應先辨識範圍並避開覆寫，而不是重設或清除不屬於任務的內容。

### 作者撰寫區塊

> 請記錄一次包含既有變更的測試情境，說明如何區分檔案、縮小提交範圍並保留原作者工作。
