## 一、必改項目（發布前必須處理）

  沒有一張使用 `raw.githubusercontent.com` 這類可公開解析的絕對網址。全站掃描確認：整個專案只有 `DAY10-Codex是什麼.md` 已改用 raw 網址，DAY04～DAY09 都還沒換。

- **建議**：發布前將六篇的圖片語法統一換成對應的 raw 網址，並同步修正六份 `DAYNN-verify.md` 中對應的核取項目。

### 2. Day08 小結預告與 Day09 實際內容不符（事實正確性）

- **位置**：Day08 小結「Day 09 會把**這段排程程式**交給 ChatGPT 做 Code Review 初篩，看它能不能找出**時區、空值與測試邊界**的問題。」

- **建議**（擇一）：
  - 修改 Day08 小結為「Day 09 會示範另一段新增的匯入互斥邏輯，練習找出並行與空值問題」，不再承諾「時區」；或

- **位置**：參考資料「Apache Maven Surefire Plugin 3.5.3」→ `https://maven.apache.org/surefire-archives/surefire-3.5.3/maven-surefire-plugin/plugin-info.html`

### 4. Day08 引用連結實為 Codex 案例、非 ChatGPT 案例（事實正確性／著作權精確度）

- **位置**：「OpenAI 官方的『Learn a new concept』範例強調縮小學習目標，並留下成果、限制與待解問題」，連結 `https://learn.chatgpt.com/use-cases/learn-a-new-concept`。
- **問題**：實際擷取該頁面，標題正上方明確標示「**Codex use case**」，內容是分派多個 subagent 平行讀論文、產生 Markdown 報告、操作檔案與跑腳本的**代理式工作流程**，屬於 Codex（獨立環境操作檔案、執行腳本）能力展示，不是 ChatGPT 對話功能案例。Day08 全篇示範的是單純問答式「預測→挑戰→驗證」，並未使用 subagent 或檔案操作。
- **重要性**：CLAUDE.md 明確要求「一律稱『ChatGPT』、『Codex』，不要混用」，Day02 又專門講兩者定位差異；此處把標示為 Codex 的案例當成 ChatGPT 佐證，容易誤導讀者，且與系列自身的用詞規範衝突。
- **建議**：改引一般 ChatGPT 對話類官方說明（例如 Prompt engineering best practices），或在文中加註「該案例原文標示為 Codex 使用情境，此處僅借用其『先縮小目標、留下限制與待解問題』方法論，非引用其 ChatGPT 功能」。

## 二、建議修改項目

### Day05：字數略超系列目標區間

- 概估中文字數（不含程式碼、圖片、參考資料）約 1,166 字，CLAUDE.md 第 4 節設定系列目標為 900～1,100 字，略超出約 60～70 字。
- 建議精簡「用同一把尺比較三個方案」段落中與後續表格重疊的說明，壓回區間內；非硬傷，不影響是否可發布。

### Day06：一則參考連結與內文對應不夠明確

- 參考資料列出兩個 OpenAI 連結（Prompt engineering best practices、How do I create a good prompt for an AI model?），但內文只籠統提及「OpenAI 對 ChatGPT 的提示建議」，第二個連結在正文中找不到明確對應的具體引用點。
- 建議：內文補一句明確指出第二個連結對應的具體建議，或評估是否移除該連結，避免「列出但未見對應內容」。

### Day09：參考資料連結指向網站首頁而非具體頁面

- 「OpenAI：ChatGPT 與 Codex 使用情境」連到 `https://learn.chatgpt.com/`（僅入口首頁），對應內文「OpenAI 目前把理解程式碼庫、執行測試與審查變更列為 Codex 工作」一句缺乏精確佐證頁面。
- 建議：改連更具體的 Codex 能力／使用情境頁面，或內文改用較保守措辭（例如「依 OpenAI 對 Codex 的產品定位」）。

### Day06：欄位收斂規則未說明（事實正確性）

- Day04 定義的 7 個原始欄位含 4 個時間欄位（`create_time`／`create_at`／`update_time`／`update_at`），Day06 程式片段直接收斂成 `createdAt`／`updatedAt` 兩欄，但未說明「4 欄如何收斂成 2 欄」這一步的處理規則（哪一欄優先、衝突如何處理）。
- 建議：補一句說明這是本篇示範規則直接寫死的選擇，避免讀者誤以為 4→2 的映射邏輯已有共識。

### 圖片長寬比無法由文字檔案驗證

- CLAUDE.md 要求圖片固定 16:9，但 markdown 純文字層級無法驗證實際 PNG 檔案比例，六篇 verify 檔案雖已勾選確認，仍建議在圖片改用 raw 網址、實際推送後，用瀏覽器或圖片檢視工具再次目視確認。
