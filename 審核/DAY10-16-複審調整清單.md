## 一、必改項目（發布前必須處理）

### 1. Day12「AGENTS.md 怎麼被套用？」整段貼近官方文件逐句翻譯（著作權合規）

- **位置**：Day12「`AGENTS.md` 怎麼被套用？」一節，描述 Codex 指令鏈建立時機、Codex home 檢查 `AGENTS.override.md`／`AGENTS.md` 的順序、從專案根目錄走到工作目錄、越靠近工作目錄的規則越晚加入可覆蓋上層要求。
- **問題**：實際擷取 OpenAI 官方文件 `learn.chatgpt.com/docs/agent-configuration/agents-md`「How Codex discovers guidance」一節逐句比對，本段幾乎是官方段落的結構重現與貼近翻譯（例如「Codex 每次執行啟動時建立一次指令鏈」對應 "Codex builds an instruction chain when it starts"；「越靠近工作目錄的規則越晚加入，可覆蓋上層要求」對應 "Files closer to your current directory override earlier guidance because they appear later in the combined prompt"），已標明出處連結，但著作權保護的是表達而非事實，這段文字重建了官方文件的段落結構與句序，落在 CLAUDE.md 第 9.1 節所稱「貼近原文逐句轉述」的高風險區。隨後 `services/reporting` 範例雖換成原創情境，敘事流程仍緊貼官方 `services/payments` 範例的呈現邏輯，屬次要風險點。
- **建議**：
  1. 打散官方文件的三段式敘述邏輯，改用自己在 Day10 專案實測 override 生效的具體操作結果切入，再用一句話帶出機制，不重現官方條列順序。
  2. 讓既有的 `day12-04-instruction-chain.png` 圖表承擔更多結構性資訊，正文只需精簡點出「override 優先、越接近工作目錄越晚套用」兩個結論。
  3. `services/reporting` 範例段落「若從根目錄啟動，之後讀到子目錄檔案也不會載入該處規則」建議換句話說，避免與官方表述過於對稱。

### 2. Day12 → Day13 案例情境切換缺乏交代（讀者清晰度／事實正確性，兩位審查者各自獨立提出同一問題）

- **位置**：Day10～Day12 案例主角是 `CsvBatchPlanner`（資料工作區批次計數缺陷，延續 Day04～09「資料工作區空間」需求書）；Day13 開場卻直接寫「今天我將它放進一個 Java 17／Maven 報表專案」，隨即出現全新的 `ReportRangeService`、`countInclusiveDays()`、套件 `com.ithome.day13.report`，與 `CsvBatchPlanner` 完全無關。
- **問題**：Day12 小結只說「Day 13 會把這份範本放進**實作專案根目錄**」，措辭仍讓讀者以為是同一個 Day10 專案的延伸；Day13 開頭也沒有一句話說明「這是新案例」「為什麼換」。對照 Day16→Day17 的寫法（Day17 開頭明確寫「把 Day 16 的交付方式套到日報服務後」並附上新需求書連結），Day12→13 是本系列中唯一沒交代清楚案例切換的地方。且 `ReportRangeService`（練習用小案例）與 Day17–23 要用的「日報服務」（既有兩年老系統）名稱相近、性質不同，容易讓讀者混淆成同一套系統的延伸。
- **建議**：
  - 在 Day12 小結加一句明確過渡，例如「Day 13 會換成另一個 Java／Maven 報表專案（`ReportRangeService`），示範同一套 `AGENTS.md` 方法如何套用到新專案」。
  - Day13 開場第一段補一句「這次不再用 Day 10 的 `CsvBatchPlanner`，改用一個獨立的報表服務練習案例，和 Day 17 之後要處理的日報服務也是兩回事」。

## 二、建議修改項目

### Day14／Day15／Day16：官方「審查窗格反映 Git 現狀」句式在系列內重複貼近翻譯（著作權合規）

- Day14「Codex 的審查畫面反映 Git 儲存庫目前的差異，不一定只有 Codex 寫入的內容」與 Day16「桌面 App 的審查窗格（review pane）可能同時包含 Codex 的修改與原有的未提交修改」，皆對應官方 `/docs/code-review`「The review pane reflects the state of your Git repository, not just what Codex edited.」同一句。單篇風險可控，但兩篇合觀時是同一句官方陳述的相近譯法重複出現。
- 建議：兩處都改寫成作者自己用 `git status` 交叉核對後的第一人稱觀察語氣，拉開與官方句式的對稱度，並避免系列內重複套用同一句翻譯。

### Day14：一則參考連結與內文對應薄弱（著作權合規）

- 「OpenAI：Integrated terminal」連結對應的是 ChatGPT 桌面 App 內建終端機抽屜功能，但正文並未討論或示範這個功能，關聯薄弱。
- 建議：移除該連結，或在正文加一句明確連到「桌面 App 內建終端機」的具體使用情境。

### Day16：一則參考連結與內文對應薄弱（著作權合規）

- 「OpenAI：Review GitHub pull requests with Codex」對應 GitHub 留言驅動 `@codex review` 的雲端審查功能，正文只泛提「推送、建 PR 與合併都是外部動作」，未實際對應。
- 建議：移除該連結，或加一句說明「Codex 也能在 GitHub PR 留言區被 `@codex review` 觸發，與本篇本機 `/review` 流程不同」。

### Day15：「Auto 組合」命名與目前官方介面標籤不一致（事實正確性）

- 文中把 `workspace-write` + `on-request` 稱為「Auto 組合」，但實際擷取官方頁面（ChatGPT 桌面 App 權限下拉選單）目前顯示標籤為「Ask for approval」，「Auto」較像 CLI 舊版 `/approvals` 選單用語。
- 建議：發文前依實際操作介面（CLI／桌面 App／IDE）重新核對當下顯示名稱，避免讀者對照畫面時找不到「Auto」這個選項。

### Day15／Day16：文中查證日期與系列實際發文日期有落差（事實正確性）

- Day15、Day16 分別寫「依 2026 年 8 月 8 日／8 月 9 日的 OpenAI 官方文件」。依系列大綱推算（Day1 開賽日 2026/08/19），Day15、16 實際發文約落在 2026/09/02～03，比文中查證日期晚約一個月，屆時官方文件若有更新，這句話會顯得過時。
- 建議：比照 Day11 的做法，移除具體日期或加註「發布前需重新查核」字樣。

### Day13：「issue」全篇未給中文對照、「堆疊」用詞可能與 stack 資料結構混淆（讀者清晰度）

- 標題與正文多處使用「issue」，全篇未比照 Day15 補上「（議題）」中譯，單篇獨立閱讀時對程式小白不友善。
- 「堆疊落在 `ReportRangeService.java:14`」指的是例外堆疊追蹤（stack trace），未加說明容易被誤讀成資料結構的「堆疊（stack）」。
- 建議：Day13 正文第一次出現「issue」時補上「（議題）」；「堆疊落在」改為「堆疊追蹤（stack trace）顯示錯誤發生在」。

### Day12：「override」「Codex home」未附中文說明（讀者清晰度）

- 「override 檔優先」的 override 是英文詞彙直接嵌入中文句子，沒有中文對照；「Codex home」也未說明是什麼。
- 建議：改為「覆寫（override）檔優先」，並在首次出現 `AGENTS.override.md` 時補一句「override 代表覆寫上層規則」；「Codex home」補註「Codex 的使用者層級設定目錄」。

### Day15：小結提前使用「commit」「Pull Request」未附中譯（讀者清晰度）

- 小結「Day 16 會實際建立 Git 分支、commit 與 Pull Request 草稿」，這兩個詞要到 Day16 開頭才正式定義，單篇讀者看到會感到突兀。
- 建議：改為「提交（commit）與 Pull Request（拉取請求）草稿」，與 Day16 的定義語感一致。

### Day10：字數略超系列目標區間（讀者清晰度）

- 概估中文字數（不含程式碼、參考資料）約 1,171 字，略高於 900～1,100 目標區間。
- 建議：精簡「面對一個動作，我先問兩個問題」或小結段落約 100 字，壓回區間內。

### Day10：JUnit 版本可能於發文時已非最新（事實正確性）

- 建議：發文前重新確認專案實際鎖定版本，或避免暗示這是「當下最新」版本。

### Day11：Maven 3.8.1 與 Java 17 搭配的已知相容性雜訊未提及（事實正確性，優先度低）
