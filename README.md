# AI 輔助問題追蹤與開發助手

> iThome 鐵人賽 30 天實作系列：以 Java 工程師的角度，驗證 ChatGPT、OpenAI API 與 Codex 能否實際參與問題整理、程式分析、測試、除錯與開發工作流程。

---

## 專案簡介

本專案是 iThome 鐵人賽「ChatGPT & Codex」主題的 30 天實作紀錄。

整個系列不以名詞介紹為主，而是從 Java 工程師在真實開發流程中可能遇到的問題出發，透過可重現的實驗，逐步建立一套：

**AI 輔助問題追蹤與開發助手**

預計涵蓋以下能力：

- 將模糊的使用者描述整理成可處理的 Issue
- 產生 Issue 標題、摘要、分類與優先級建議
- 將自然語言轉換成結構化 JSON
- 使用 Spring Boot 串接模型 API
- 建立受限制的工具呼叫流程
- 分析 Java Stack Trace 與測試失敗
- 使用 Codex 閱讀、分析及修改 Java 專案
- 產生與驗證 JUnit 測試案例
- 比較 AI 修改前後的 Git diff
- 在 AI 建議與實際執行之間加入人工核准
- 保存 Prompt、輸出、驗證結果、失敗原因與修正紀錄

---

## 系列核心問題

這個系列希望回答的不是「AI 能不能寫程式」，而是更具體的工程問題：

> ChatGPT、OpenAI API 與 Codex，究竟適合參與 Java 開發流程中的哪些環節？  
> 哪些結果可以透過程式驗證？哪些決策仍然必須由工程師負責？

---

## 核心工作流程

```text
模糊問題輸入
    ↓
AI 整理 Issue
    ↓
結構化 JSON
    ↓
Spring Boot REST API
    ↓
工具選擇與權限限制
    ↓
Codex 分析或修改程式碼
    ↓
JUnit 與靜態檢查驗證
    ↓
人工核准
    ↓
保存實驗結果、限制與結論
```

---

## 專案目標

1. 建立一個可持續演進的 Java AI 實作專案。
2. 驗證 AI 輸出是否能被程式、測試或人工規則檢查。
3. 清楚區分 ChatGPT、OpenAI API、Codex、模型能力與第三方框架。
4. 記錄成功與失敗案例，不只展示理想結果。
5. 建立一套適合 Java 工程師採用的 AI 協作流程。
6. 在 30 天結束後，整理出 AI 適合與不適合介入的開發環節。

## 預計 API

以下為系列預計逐步完成的介面，最終內容可能依實驗結果調整。

### 分析 Issue

```http
POST /issues/analyze
Content-Type: application/json
```

預計輸入：

```json
{
  "description": "會員登入後偶爾會被導回登入頁"
}
```

預計輸出：

```json
{
  "title": "會員登入後 Session 可能異常失效",
  "summary": "使用者完成登入後，偶爾會再次被導回登入頁。",
  "category": "BUG",
  "prioritySuggestion": "HIGH",
  "missingInformation": [
    "發生環境",
    "重現步驟",
    "瀏覽器版本",
    "相關日誌"
  ]
}
```

> 上述 JSON 僅為預計格式，實際 Schema 將於系列實作與驗證後確定。

### 分析 Stack Trace

```http
POST /diagnostics/stack-trace
Content-Type: application/json
```

預計輸出內容包含：

- 錯誤摘要
- 可能原因
- 關鍵 Stack Frame
- 驗證步驟
- 修正建議
- 不確定資訊
- 是否需要人工核准

## 驗證原則

本系列不會直接把 AI 輸出視為正確答案。

每個重要結果至少使用一種方式驗證：

- 依照官方文件確認產品或 API 行為
- 使用 JSON Schema 或 Java 型別驗證輸出
- 執行 JUnit 測試
- 執行程式確認結果
- 比較 Git diff
- 重複執行相同實驗
- 建立固定測試資料集
- 由人工依明確標準評分
- 與未使用 AI 的基準方法比較

## AI 與人工責任邊界

AI 可以協助：

- 整理問題
- 提出分類建議
- 產生初稿
- 分析錯誤訊息
- 提出除錯假設
- 產生測試草稿
- 建議程式碼修改
- 協助整理 Review 意見

工程師仍需負責：

- 確認需求
- 判斷優先級
- 驗證技術結論
- 審查程式碼修改
- 決定是否執行工具
- 管理資料與權限
- 核准正式變更
- 承擔最終系統品質

## 安全與資料隱私

本專案的實驗資料應遵守以下原則：

- 不提交 API 金鑰
- 不提交真實密碼或 Token
- 不上傳公司內部程式碼
- 不使用真實客戶個資
- Stack Trace 應移除帳號、IP、路徑與內部網址
- 使用 `.env.example` 說明設定，不提交 `.env`
- 工具呼叫採白名單
- 破壞性操作預設禁止
- 程式修改必須經過 Git diff 與測試
- 對外部輸入進行 Prompt Injection 風險檢查
- 高風險操作保留人工核准步驟
