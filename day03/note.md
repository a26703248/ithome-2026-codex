# Day 03：同一個問題問五次 ChatGPT，五份答案有哪些差異？

> 📝 *本系列為 iThome 鐵人賽學習筆記，屬個人教學與非商業用途；文中法規與標準內容均以自己的話轉述並註明出處，非逐字引用。*

> 🤖 *工具參與揭露：ChatGPT 依固定提示產生本文分析的五份原始輸出；Codex 協助執行瀏覽器實測、保存資料、比較差異、產生配圖與形成文章草稿。正式發布前仍須由作者人工查核，並由作者對內容負最終責任。*

Day 01 把一句「登入功能怪怪的，有時候會失敗」整理成人工基準；Day 02 再把問題追蹤項目（Issue）欄位分成原始證據、人工智慧（Artificial Intelligence，以下簡稱 AI）整理、AI 建議與人類決定。接下來要面對一個會直接影響系統設計的問題：把相同內容交給 ChatGPT 五次，是否會得到相同答案？

這個問題不能只用「一樣」或「不一樣」回答。兩份回答可能文字不同，但核心意思相同；也可能格式完全一致，卻同時補進原文沒有的資訊。前者影響畫面呈現與程式解析，後者影響事實正確性與責任歸屬。Day 03 因此不只比對字串，而是分別觀察結構、文字、語意、清單與證據邊界。

![同一份問題進入五次新的對話後產生相似但不同的 Issue 草稿](https://raw.githubusercontent.com/a26703248/ithome-2026-codex/main/%E5%9C%96%E6%AA%94/Day03/Day03-01-five-independent-runs.png)

## 「穩定」至少有五種不同意思

本文沿用六個欄位：標題（Title）、摘要（Summary）、實際結果（Actual Result）、預期結果（Expected Result）、缺少資訊（Missing Information）與分流狀態（Triage Status）。

假設五次輸出都有 `Title`，可以說格式穩定；若五次標題逐字相同，才能進一步說字串穩定。若文字不同但都描述登入偶發失敗，則是語意近似。若每次列出的追問不同，則要比較集合。最後，即使前四項都穩定，只要輸出把未知需求寫成已知事實，仍然不能採用。

本次實驗使用下列五個觀察層次：

| 層次 | 要問的問題 | 例子 |
| --- | --- | --- |
| 結構一致性 | 指定欄位是否每次都出現？ | 五次都有六個段落 |
| 逐字一致性 | 文字是否完全相同？ | Title 五次是否同一句 |
| 語意一致性 | 不同寫法是否表達相同意思？ | 「待補充資訊」與「需要更多資訊」 |
| 集合一致性 | 清單項目是否有增減？ | 是否每次都詢問網路環境 |
| 證據合規 | 每個肯定主張能否回到原始資料？ | 原文沒寫 Expected Result，就不能假裝已知 |

這五層不能互相替代。對人類閱讀而言，「待補充資訊」和「需要更多資訊」幾乎相同；對只接受固定狀態碼的程式而言，兩者卻是不同字串。另一方面，完美一致地重複一項沒有證據的內容，只代表錯誤很穩定，不代表品質良好。

## 實驗設計：相同輸入，五個新的對話

本次使用 ChatGPT 未登入網頁介面執行五次。每次都開啟新的對話頁面，沒有把前一次回答或追加訊息帶入下一次。固定原始回報、完整提示與欄位順序；沒有刻意要求模型每次改寫。

![固定輸入、提示與對話條件後依序保存五次輸出](https://raw.githubusercontent.com/a26703248/ithome-2026-codex/main/%E5%9C%96%E6%AA%94/Day03/Day03-02-controlled-experiment.png)

### 原始回報

```text
登入功能怪怪的，有時候會失敗。
```

### 五次共用的完整提示

```text
請將以下使用者回報整理成一張可處理的軟體 Issue。
只能使用原文提供的資訊；不知道的內容請寫「未知」，不可自行補充。
請依序輸出：
1. Title
2. Summary
3. Actual Result
4. Expected Result
5. Missing Information
6. Triage Status

使用者回報：
登入功能怪怪的，有時候會失敗。
```

這不是本系列最終版提示詞。Day 06 至 Day 08 才會逐步比較提示長度、建立 Issue 提示與處理未知資訊；本日只需要一份固定、容易檢查的實驗指令。六個欄位刻意混合 Day 02 的不同責任層級：Title、Summary 與 Actual Result 偏向有來源的整理；Missing Information 與 Triage Status 屬於建議；Expected Result 則必須尊重規格與責任邊界。

## 五次輸出：骨架一致，內容並非逐字相同

先看最容易量化的結果。

| 指標 | 結果 |
| --- | ---: |
| 收到完整回答 | 5／5 |
| 六個指定欄位全數出現 | 5／5 |
| 與其他執行完全重複的完整回答 | 0／5 |
| Title 逐字相同 | 5／5 |
| Actual Result 逐字相同 | 5／5 |
| Summary 的不同文字版本 | 5 |
| Expected Result 的不同文字版本 | 5 |
| Missing Information 項目數 | 每次 8～9 項 |
| Triage Status 的不同文字版本 | 5 |

「與其他執行完全重複的完整回答為 0／5」不表示所有欄位都在變。實際情況恰好相反：外層結構完全一致，Title 與 Actual Result 也完全一致；其餘欄位的措辭、清單內容或詳細程度發生變化。

### 第 1 次執行（Run 1）的完整輸出

以下原始輸出中的 `App` 是應用程式（Application）的常見簡寫。輸出文字為實驗證據，因此保留原貌，不在引用區塊內統一用詞。

```text
1. Title
   登入功能有時候會失敗

2. Summary
   使用者回報登入功能異常，表示有時候登入會失敗。

3. Actual Result
   登入有時候會失敗。

4. Expected Result
   登入功能應能正常完成，不應發生偶發性失敗。

5. Missing Information
   - 發生環境：未知
   - 發生頻率：未知
   - 重現步驟：未知
   - 錯誤訊息：未知
   - 使用裝置：未知
   - 作業系統：未知
   - App／瀏覽器版本：未知
   - 帳號類型：未知
   - 發生時間：未知

6. Triage Status
   待補充資訊（資訊不足，無法進一步確認或重現）
```

## 穩定欄位與變動欄位

![五份輸出具有共同骨架，但文字、清單與項目數有所不同](https://raw.githubusercontent.com/a26703248/ithome-2026-codex/main/%E5%9C%96%E6%AA%94/Day03/Day03-03-stable-and-variable.png)

### Title 與 Actual Result：本次樣本逐字一致

五次 Title 都是：

```text
登入功能有時候會失敗
```

五次 Actual Result 也都是：

```text
登入有時候會失敗。
```

這兩個欄位可以直接追溯到原始回報的「登入」與「有時候會失敗」，沒有增加環境、根因或影響。依 Day 02 的責任模型，它們可視為 L1 的 AI 整理草稿。不過，「五次一致」只描述這個案例，不足以推論所有輸入都會穩定。

### Summary：意思接近，表達仍有五種

五次摘要都保留登入偶發失敗的核心，但分別使用「表示有時候」「登入有時候」「並非每次」與「發生情況不固定」等寫法。Run 4 與 Run 5 增加的說明仍可由「有時候」合理轉述，沒有創造新的環境或根因。

對人類審閱而言，這些差異通常不妨礙理解；若下游系統拿整段文字當識別鍵、快取鍵或測試預期值，就會得到五個不同結果。工程設計不能把語意近似誤當成字串相等。

### Missing Information：共同缺口之外，每次都有增減

五次都提到發生環境、頻率、重現步驟、錯誤訊息、作業系統與版本，但不是所有追問都固定出現：

| 只在部分執行出現的項目 | 出現情況 |
| --- | --- |
| 帳號類型 | Run 1、2 |
| 網路環境 | Run 3、4 |
| 發生時間 | Run 1、2、3、5 |
| 是否可穩定重現 | Run 5 |
| 使用裝置 | Run 1、2、3、4 |

這代表模型能提出有用的追問候選，卻不能保證每次自動產生相同的必問清單。若團隊規定「錯誤訊息、發生時間與版本」必須蒐集，這些項目應寫進固定規則或結構驗證，而不是依賴模型臨場想到。

### Triage Status：方向相同，不是同一個狀態值

五次分別產生：

1. `待補充資訊（資訊不足，無法進一步確認或重現）`
2. `待補充資訊（資訊不足，需進一步確認）`
3. `待補充資訊`
4. `待確認（資訊不足）`
5. `需要更多資訊才能進一步調查。`

人類可以判斷五句都指向「資訊不足，需要補充」；工作流程引擎卻不應直接接受五種自由文字。正式系統需要受控列舉值，例如固定狀態代碼，再把自然語言留給說明欄。Day 03 尚未建立最終資料格式，但已足以證明：語意一致不代表可以跳過結構驗證。

## 最關鍵的失敗：五次都補寫了未知的 Expected Result

原始回報只說登入有時候失敗，沒有產品規格，也沒有說明登入成功後應進入哪裡。提示詞已要求「不知道的內容請寫未知，不可自行補充」。理想輸出因此應該是：

```text
Expected Result：未知；待產品規格或需求負責人確認。
```

實際五次輸出卻分別寫成「應能正常完成」「應能正常運作」或「不應發生間歇性登入失敗」。這些句子符合一般常識，也很可能符合真正需求，但它們仍然不是原始回報提供的事實。

本次樣本中，Expected Result 符合「未知」規則的次數是 **0／5**。這個結果比文字變動更重要，因為它顯示一份輸出可以同時具備完整格式、流暢語句與合理內容，卻仍跨越證據邊界。若把這種內容直接寫進正式 Issue，後續工程師可能把模型的常識推測誤認為已確認驗收條件。

這並不證明 ChatGPT 永遠無法遵守未知規則，也不能由五次樣本推估一般性失敗率。它只證明：對這份提示與這個案例而言，重複五次仍沒有自動消除風險。

## 把差異放回 Day 02 的責任模型

![AI 整理與建議都必須經過來源檢查及人工核准閘門](https://raw.githubusercontent.com/a26703248/ithome-2026-codex/main/%E5%9C%96%E6%AA%94/Day03/Day03-04-responsibility-gate.png)

| 差異位置 | Day 02 層級 | 可以如何使用 | 不能直接做什麼 |
| --- | --- | --- | --- |
| Title、Summary、Actual Result | L1：AI 整理 | 保存為有來源的草稿，讓人核對 | 覆寫原始回報 |
| Missing Information | L2：AI 建議 | 提供追問候選，由分流者排序 | 把某次沒列出的項目視為不重要 |
| Triage Status | L2 候選；正式狀態轉換涉及 L3 | 映射到受控狀態候選 | 用自由文字直接轉換流程狀態 |
| Expected Result | 涉及 L3：規格擁有者決定 | 標示未知並要求規格證據 | 將模型推測當成正式需求 |

這張表說明，輸出變異不是單純的文字風格問題。L1 的措辭差異通常容易人工處理；L2 清單差異會改變追問與分流；涉及 L3 的未知資訊一旦被模型補滿，則可能改變開發與驗收依據。差異發生在哪個責任層級，決定了需要多強的控制。

## 從實驗轉成工程控制

Day 03 還沒有進入應用程式介面（Application Programming Interface，以下簡稱 API）或 Java 實作，但已能確定後續系統需要下列控制：

1. **原始回報與 AI 草稿分開保存**：任何改寫都不能消除來源。
2. **欄位逐項驗證**：不能只確認六個段落都存在。
3. **未知值使用明確表示**：沒有規格證據時，Expected Result 必須保持未知。
4. **必問清單由規則保證**：模型可以補充候選，不能取代最低必要欄位。
5. **狀態使用受控值**：自由文字先映射成候選，再由規則或授權人員確認。
6. **記錄模型可見標籤與限制**：精確模型或參數看不到時就寫未知，不自行推測。
7. **以多次執行測試變異**：單次成功輸出不能代表穩定性。

其中部分控制會在後續日次逐步實作。Day 09 將處理結構化輸出，Day 10 將處理格式錯誤，Day 28 才會把人工核准接入完整工作流程。此處先保存需求，不提前把尚未驗證的設計寫成完成品。

## 本日限制：五次測試不是一般性統計

本實驗的範圍刻意很小：

- 只有一個模糊登入案例。
- 只有一份提示詞。
- 只有五次執行。
- 使用未登入網頁介面。
- 介面只顯示 `ChatGPT`，精確模型識別碼未知。
- 溫度、種子與路由資訊未知。
- 五次位於同一瀏覽器工作階段，但每次沒有共享對話訊息。
- 沒有使用 Day 04 才會建立的人工品質評分表。

因此，本文不宣稱得到穩定率、錯誤率或模型間比較，也不把差異歸因於某個不可見參數。若日後介面或模型更新，應重新執行，而不是把這五份結果永久視為產品規格。

## 今日結論：答案會變，但真正要管的是變在哪裡

本次五次測試得到六項結論：

1. 五份完整回答都不完全相同，因此不能假設相同提示必然產生相同字串。
2. 結構並未失控：六個指定欄位五次都出現，Title 與 Actual Result 也逐字一致。
3. Summary 與 Triage Status 的文字不同，但核心語意接近。
4. Missing Information 每次有 8～9 項，集合不完全相同；必問資料需要額外規則保證。
5. Expected Result 五次都跨越證據邊界，說明「格式穩定」與「內容可採用」是兩件事。
6. AI 輸出必須依責任層級接受來源檢查、結構驗證與人工核准，不能只看文字是否流暢。

Day 03 已回答「會不會不同」，但尚未回答「哪一份比較好」。Day 04 將建立人工評分標準，把忠實性、資訊完整性、可讀性、可行動性與責任邊界轉成可重複使用的檢查項目。
